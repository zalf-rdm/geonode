# Upstream divergences

Where `zalf-rdm/geonode` differs from upstream `GeoNode/geonode`, and why.

**Maintenance rule:** every change that adds to, or alters, fork-only code belongs
in this file in the same commit. If a change touches upstream code, say so
explicitly — those are the ones that hurt at merge time.

Each area below names the files involved so a merge conflict can be traced back
to an intentional decision rather than re-litigated from scratch.

---

## 1. DataCite / RDM metadata extension (`geonode.base`)

The fork extends `ResourceBase` with DataCite-aligned metadata so published
datasets can be minted and described to RDM standards.

**`ResourceBase` fields added:** `abstract_translated`, `date_type`, `funders`,
`method_description`, `other_description`, `related_identifier`,
`series_information`, `subtitle`, `table_of_content`, `technical_info`,
`title_translated`, `use_contraints`.

**Migration branch.** This extension runs on its own migration lineage that was
later merged back into upstream's:

```

  →  0090_auto_20230330_0718  →  0091_auto_20230331_0757

0096_merge_0088_auto_20231019_1244_0095_auto_20230331_0923
```

Upstream occupies the same numbers with different migrations
(`0086_linkedresource`, `0087_thesauruskeyword_icon`, `0089_resourcebase_advertised`,
`0091_create_link_asset_alter_link_type`, …). **Expect collisions on every
upstream merge that adds `base` migrations** — a new merge migration is the
normal resolution, not renumbering.

**Seed data.** `geonode/base/fixtures/initial_data.json` ships the controlled
vocabularies: 18 `base.relatedidentifiertype` rows and 27 `base.relationtype`
rows. Because `label` is the PK on both models, these rows *are* their own
identity — the integer `pk` values in the fixture are vestigial and ignored on
load.

> **Trap for tests.** `GeoNodeBaseTestSupport` loads `initial_data.json`
> (`geonode/tests/base.py:52`), so `DOI`, `IsSourceOf` and the rest already exist
> before any test body runs. Creating one with `objects.create(label=...)` raises
> `IntegrityError: duplicate key value violates unique constraint
> "base_relatedidentifiertype_pkey"`. Use
> `get_or_create(label=..., defaults={"description": ...})`, and keep
> `description` out of the lookup — several fixture rows carry an empty
> description (e.g. `IsSourceOf`), so matching on it misses and collides anyway.

**API surface:** `geonode/base/api/serializers.py`, `geonode/base/api/views.py`.
Tests: `RelatedIdentifierApiTests` in `geonode/base/api/tests.py` (issue #784).

## 2. ORCID-only login via Keycloak (`geonode.people`)

ORCID is brokered through ZALF's Keycloak instance and consumed with
django-allauth's `openid_connect` provider. GeoNode never talks to orcid.org
directly and **does not use the ORCID Members API** — the declared scopes are
`openid`, `email`, `profile`.

- `geonode/settings.py` — the `# ORCID` block, roughly lines 2267–2387, plus
  `INSTALLED_APPS += ("geonode.zalf",)` at the end of the file.
- `geonode/people/models.py:147` — `Profile.orcid_identifier` and
  `get_orcid_url()`.
- `geonode/people/migrations/0031_merge_20210205_0824.py` — adds the field.
- `geonode/people/adapters.py` — login plus the "log out of GeoNode and ORCID"
  flow through Keycloak's `end_session_endpoint`.
- `geonode/people/profileextractors.py` — `OrcidExtractor`.
- `geonode/people/tests_orcid_display.py`.

Full writeup: [`orcid_only_login.md`](orcid_only_login.md), including the
member-integration compliance table.

> **Open question.** `OrcidExtractor.extract_organization`
> (`profileextractors.py:247-263`) parses `affiliation.organization.
> disambiguated-organization.disambiguation-source` — hyphenated keys from the
> ORCID *record API* v3.0, not OIDC claims. The `profile` scope does not supply
> an `affiliation` object, and no test covers this path. Either a Keycloak claim
> mapper fetches the record, or the branch silently returns `None` on every
> login. Unresolved as of 2026-10-05.

| 2026-11-09 | **Download packages for published data collections** (#659). Upstream GeoNode offers no map download: `DownloadArrayLinkField` returns `[]` for maps. Researchers clicked through one download per layer and document. A map now gets **one ZIP of everything anonymous visitors may download**, which after publication is exactly what the publication made public. **This replaces the custom Java WPS process sketched in #659**: building is Python and Celery only, and the bytes are served by object storage, not by GeoServer or the institute's uplink. **(1) Contents.** The task reuses what GeoNode already keeps. It takes each resource's own `LocalAsset` (the importer's original upload, a document's file) and falls back to GeoNode's dataset export only for datasets without one. That export is `DatasetDownloadHandler`'s WPS `gs:Download` with the same template and format rules, subclassed to take the resource directly and to **stream to disk**, because upstream `process_dowload` buffers the whole response in memory. `MANIFEST.txt` records each file's origin and SHA-256. **(2) Storage: `S3Asset` and `S3AssetHandler`, new in the fork.** GeoNode ships only `LocalAssetHandler`, whose storage is hard-wired to the filesystem. The new handler is configured only by `ZALF_DOWNLOAD_S3_*`, not the global `AWS_*` settings, so it serves any S3-compatible provider (Hetzner first) and never touches GeoNode's other storage. It sets `request_checksum_calculation`/`response_checksum_validation` to `when_required`, because boto3 ≥ 1.36 sends CRC checksums by default and S3-compatible providers have rejected them. It sets no canned ACL, since public mode relies on a bucket policy. Each upload gets a fresh key, so a rebuild never overwrites the object being served. `clone` copies server-side (GeoNode clones a map's assets with the map), and `post_delete` deletes the object. Without a bucket, the package is a `LocalAsset`. **(3) Authorization is by *view* on the map, through a ZALF endpoint, not GeoNode's asset endpoint.** `get_perms_response` requires `download_resourcebase` on the linked resource, and `_build_public_perm_spec` deliberately grants maps view only. Granting download on maps instead would have changed publication semantics and required re-permissioning every published map. The relaxation is safe because the package is built from publicly downloadable files only. **Consequence to know:** a package is a snapshot, so restricting a resource after a build leaves it in the package until the next rebuild. **Also by design: GeoNode does not gate the bytes.** It checks the map's visibility when it issues the 302, not per byte, so the presigned URL the visitor receives is a forwardable capability for `ZALF_DOWNLOAD_S3_URL_EXPIRY` and is visible in any browser's network log. That is acceptable only because a package contains nothing that is not already publicly downloadable, and the repository's data is open; the endpoint is for discovery and download counting, not access control. S3 cannot be made to enforce GeoNode permissions -- its API has no authorizer hook, so per-request enforcement would need a reverse proxy doing `auth_request` against GeoNode and streaming from the bucket, sited in the bucket's own datacentre to keep the bytes off the institute's uplink. Not built. The expiry stays at an hour on purpose: SigV4 validates it when a request is accepted, so a long transfer finishes, but a shorter window would fail a resumed multi-GB download. **(4) Triggers.** The publish endpoint takes `build_download_package` (default `true`, a checkbox in the client's publish dialog) and queues the build with `transaction.on_commit`, after the public permissions are written. Existing maps are covered by `POST /api/v2/maps/<id>/download_package/` (data stewards), a steward button on published maps, the *Download packages* admin action, and `manage.py build_download_packages`. One build per map at a time; a row stuck in `building` past the task's time limit may be restarted. A rebuild links the new asset before deleting the old one, so the download never disappears. **(5) Activation switch.** `ZALF_DOWNLOAD_PACKAGE_ENABLED` is **off unless a deployment sets it** (changed from defaulting on, 2026-11-10): the feature writes multi-GB archives and uploads them to a bucket, so a deployment with no bucket and no scratch space on a PVC should stay inert rather than fill its disk on the first publication. Nothing in `zalf-project` or `geonode-k8s` set the variable, so **every environment has to add it**, `repository-e`/`fizz` included, or packages silently stop being offered; the dev `.env` files and `.devcontainer/.env_sample` now carry it explicitly. It is checked by every entry point — publication, the map endpoint, the admin action and the management command — and the download endpoints answer 404 while it is off, which is how the client learns to hide its buttons (`enabled` in the state payload). Packages already built are **kept, not deleted**, so switching it back on restores them; `download_package_status` keeps reporting while it is off, and a build queued before the switch was flipped is recorded as failed rather than left pending, which would block the next request until the task's time limit. The `S3AssetHandler` registration and the queue stay in place when the feature is off, so earlier packages remain resolvable (asset admin, deleting a map) and in-flight tasks can drain. **(6) Operations.** The task runs on the new queue `zalf.download_package`. The default worker consumes it, since `celery-cmd` only excludes `harvesting`. Scratch space is `ZALF_DOWNLOAD_PACKAGE_BUILD_ROOT` on the statics PVC, because `/tmp` is an `emptyDir` in the geonode-k8s chart and a multi-GB build there risks pod eviction. The bucket is inspected with `s3cmd` using a config of its own; deleting an object that way leaves the `DownloadPackage` row and the `Asset` behind, so removal goes through the asset admin or a rebuild (`build_download_packages --map <ID>`; there is no `--rebuild` flag, since building a map that already has a package *is* the rebuild). **(7) Validation.** A row records what its last build concluded, so nothing in it notices an object removed, truncated or never uploaded. `download_package_checks.py` asks the storage instead -- object present, size as built, and with `--deep` the ZIP read and the sha256 compared -- and classifies each package as ok, pending, missing, stale (a build whose worker died), failed, no-asset, mismatch, corrupt, gone or unreachable. It also finds objects under the prefix that no asset references and assets no row references, which is how a failed delete or a restored database is caught. One implementation, two front ends: `manage.py validate_download_packages` (with `--fail-on-broken` for cron) and a *Validate storage* page plus a per-row action in the Download packages admin. `S3Asset` is registered in the admin as well, since GeoNode registers only `LocalAsset` and a dangling S3 asset could otherwise not be inspected or removed through the admin at all. Checks never run on the changelist itself: one request per row would make the list as slow as the bucket is far away. `s3_client(for_check=True)` adds a 5 s connect / 15 s read timeout with 2 attempts, so a wrong endpoint fails in seconds instead of minutes. **Documented in** `zalf_docs/download_packages.md`: contents, storage, the switch, every setting, all three management commands with their options, the endpoints, the admin pages, validation and a troubleshooting table. **Verified:** 73 new tests (`test_download_packages.py`, including the activation switch and validation) and all 250 `geonode.zalf` tests pass; the upstream `geonode.assets` suite passes with the second handler registered; `makemigrations --check` is clean.
